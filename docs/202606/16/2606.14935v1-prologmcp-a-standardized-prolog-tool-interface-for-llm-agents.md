## 摘要
前沿推理调优的语言模型在深度演绎任务上仍然失败，并且通过扩展内部推理来提高性能的成本难以扩展。符号委派提供了一条补充路径：语言模型翻译问题，而求解器执行推理。然而，当前用于逻辑编程的自动形式化管道通常是特制的集成，与特定任务或代理绑定。我们引入了PrologMCP，一个任务无关的开源服务器，通过模型上下文协议（MCP）将Prolog暴露为一个有状态工具。其紧凑的工具接口、结构化的错误报告以及每会话隔离，使得翻译-运行-检查-修复循环成为支持MCP的代理的可重用原语。我们评估了通过PrologMCP增强的形式化代理，与标准及推理LLM（Claude Sonnet 4.6、GPT-4.1和o4-mini）在PARARULE-Plus的两个子集上：一个通用样本和一个更具挑战性的针对自然语言推理特定失败模式的样本。在通用样本上，形式化代理匹配或超过推理LLM（准确率1.00 vs.\ 1.00 / 0.998），相对于标准模型（GPT-4.1为0.762）提升最大。在挑战性子集上，形式化代理保持近乎完美（1.00 / 0.99），而推理LLM下降至0.95 / 0.94。这些结果表明，通过MCP将推理委托给Prolog是扩展自然语言推理的稳健且可检查的替代方案。

## Abstract
Frontier reasoning-tuned language models still fail on deductive tasks at depth, and the cost of improved performance through extended internal reasoning scales poorly. Symbolic delegation offers a complementary route: a language model translates the problem, while a solver performs the inference. However, current autoformalization pipelines for logic programming are typically bespoke integrations tied to particular tasks or agents. We introduce PrologMCP, a task-agnostic, open-source server that exposes Prolog as a stateful tool through the Model Context Protocol (MCP). Its compact tool interface, structured error reporting, and per-session isolation make the translate-run-inspect-repair loop a reusable primitive for MCP-capable agents. We evaluate a formalizer agent enhanced with PrologMCP against standard and reasoning LLMs (Claude Sonnet 4.6, GPT-4.1, and o4-mini) on two subsets of PARARULE-Plus: a general-purpose sample and a more challenging one targeting a specific failure mode of natural-language reasoning. On the general sample, the formalizer matches or exceeds reasoning LLMs (accuracy 1.00 vs.\ 1.00 / 0.998), with the largest gains over standard models (0.762 for GPT-4.1). On the challenging subset, the formalizer remains near-perfect (1.00 / 0.99) while reasoning LLMs drop to 0.95 / 0.94. These results suggest that delegating inference to Prolog via MCP is a robust and inspectable alternative to extended natural-language reasoning.

## 1. 核心问题与整体含义

- **研究动机**：前沿推理调优的大型语言模型（LLM）在深层次演绎推理任务上仍会失败，且通过扩展内部推理（增加“思考”token）来提高性能的成本增长迅速且回报递减。相比之下，符号求解器（如Prolog）能保证正确性且计算可预测。

## 2. 方法论：核心思想、关键技术细节

- **核心思想**：**translate–run–inspect–repair循环**。LLM将自然语言问题翻译为Prolog程序，通过MCP服务器提交给Prolog求解器执行查询，检查结构化的输出/错误，若失败则修改形式化并重试。这分离了“形式化翻译”和“符号推理”两个能力。
- **关键技术细节**：
  - **MCP服务器架构**：分为三层——（1）Python MCP服务器，提供工具声明、验证和分发；（2）会话注册表，管理隔离的Prolog子进程池（TTL、LRU、线程安全）；（3）Prolog harness（harness.pl），通过stdin/stdout通信，处理JSON命令。
  - **工具接口**：暴露8个操作工具 + 1个管理工具：
    - `consult_text`：从源代码加载新会话，返回load_id、诊断消息。
    - `run_goal`：执行目标查询，支持深度限制（`call_with_depth_limit`）、答案数量限制。
    - `inspect_predicate`：检查谓词定义（子句、arity、类型等）。
    - `get_source`：重建当前模块的源代码。
    - `replace_predicate`：替换单个谓词的子句（支持修复）。
    - `list_messages`：返回累积的诊断消息。
    - `run_tests`：执行plunit单元测试。
    - `trace_goal`：通过元解释器生成证明树。
    - `close_session`：关闭会话并释放资源。
  - **会话隔离**：每个会话运行在独立`swipl`子进程中，使用唯一模块名，避免命名冲突。
  - **非致命编译**：语法错误不会导致加载失败，而是通过`message_hook`捕获并返回诊断，代理可据此修复。
  - **结构错误报告**：所有错误以`{ok: false, error: {kind, message, prolog_term}}`格式化，不终止会话。
- **形式化代理实现**：模型输出Prolog程序（`<prolog>...</prolog>`标签内）和查询目标（`<goal_true>...</goal_true>`标签内），解析后调用`consult_text`和`run_goal`。若失败则重试，最多`max_attempts`（5次）。要求符合PARARULE-Plus的特殊否定语义（正文否定仅初检事实，查询否定用完整闭包），通过编码`initially/2`约定实现。

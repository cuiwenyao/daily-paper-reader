## 摘要
大型语言模型（LLM）代理部署在车辆中，必须在每一轮满足书面操作策略：一个幻觉标识符、遗漏的强制副作用或过早的完成声明都会导致任务失败。我们提出了AgentGuardUtil，这是我们对CAR-bench第一赛道的参赛作品，它将AI规划器（LLM）视为基于现实的验证-修订循环中一个易错的提议者。其核心创新是一个运行时策略编译器：随每个对话提供的自然语言策略，每个策略被编译一次，编译成类型化的机器可检查规则，其中一部分规则具有可执行形式。一个确定性的义务引擎根据实时工具结果和草稿本身的模拟写入后状态来解释这些规则，发出带有计算参数的确切补救调用，而不是自然语言提醒。围绕该引擎，25个确定性门控（标识符来源、模式和枚举有效性、先收集后行动、确认和未来时间协议）以及一个LLM批判器产生分级发现，驱动一个针对pass k指标调整的有界修订循环。

## Abstract
Large Language Models (LLMs) agents deployed in vehicles must satisfy a written operating policy on every turn: a single hallucinated identifier, omitted mandatory side-effect, or premature completion claim fails the task. We present AgentGuardUtil, our entry to CAR-bench Track~1, which treats the AI planer (LLM) as a fallible proposer inside a grounded verify-and-revise loop. Its core novelty is a runtime policy compiler: the natural-language policy shipped with each conversation is compiled, once per policy, into typed machine-checkable rules, a subset of which receive an executable form. A deterministic obligation engine interprets these rules against live tool results and the simulated post-write state of the draft itself, emitting the exact remedial calls with computed arguments rather than natural-language reminders. Around this engine, 25 deterministic gates (identifier provenance, schema and enum validity, gather-before-act, confirmation and future-time protocols) and an LLM critic produce tiered findings that drive a bounded revision loop tuned for the pass k metric.

## 2. 方法论：核心思想、关键技术细节与算法流程

### 2.1 核心设计思想
- **学生-教师分解**：LLM（学生）只负责提出草稿动作；确定性验证框架（教师）审查每份草稿、返回具体发现，并在任何动作到达模拟驾驶员之前重新验证修订。
- **假设-保证纪律**：只假设学生"有能力但易犯错"，而策略合规、数据基础、政策遵循等保证则由从对话自身产物（策略文本、工具模式、观察数据）编译出的确定性检查来承担，不依赖学生行为。

### 2.2 系统架构（图 1 与算法 1）
单次回合的流程分为：
1. **首次回合策略编译**：运行时策略编译器将自然语言策略 Π 翻译成类型化、可执行的规则集 R，并按 hash(Π) 缓存。
2. **提取请求**：扫描新用户消息，将显式请求追加到待办问询清单 L，供完成门控后续核对。
3. **多模态投票**：若草稿会改变环境状态且投票策略开启，同一提示词采样 n 次，取出现最多的动作集合（工具调用的多重集，带归一化参数）。
4. **验证-修订循环**（最多 R 轮）：
   - 确定性门控产生 **硬发现**（F_hard，独立成立）；
   - 同一门控产生 **建议候选**（F_adv），由 LLM 批判器（CRITIC）确认或丢弃——批判器既不能新增发现，也不能推翻硬发现；
   - 若合并后的分级发现 F 非空，则 REVISE 带发现重提示学生，重新进入验证。
5. **安全网（safety net）**：若草稿被修订过且仍持有硬发现，再以 R 轮循环之外的 REVISE_esc 单独处理一次（可启用升级模型）。
6. **清理与放行**：SANITIZE 去除不可播报标记，验证过的工具调用到达环境、净化后的回复到达模拟驾驶员。

### 2.3 运行时策略编译
- 每条规则 r = ⟨id, κ, Tr, ρ⟩，κ 为类型（前置条件、自动动作、确认、禁止、披露、约束、选择），Tr 为触发工具集合（对照实时工具清单验证），ρ 为命令式要求。
- 复合子句拆分为原子规则（一条条件对应一个补救措施）。
- 二次聚焦扫描将状态条件规则转化为**可执行形式**：

  er = g, φ, ◁, v, ω

  其中 g 为读取工具，φ 为带一个通配符的字段名模式，◁ 为比较运算符，v 为阈值，ω(x) = ⟨u, β(x)⟩ 为义务模板（将匹配项绑定到工具 u 的参数）。
- **参数验证**：编译器读取真实工具签名；参数无法验证的义务会被丢弃并降级为建议性规则——引擎只能增加精度，不能强制无效调用。
- **示例**：策略"打开空调时，若车窗打开超过 20% 则自动关闭"，被编译为规则 e011 = get_vehicle_window_positions, window_*_position, >, 20, open_close_window(⟨item⟩, 0)。当观测到位置 25/100/0/10 时，恰好两条义务存活，并带证据"window_driver_position = 25 > 20"逐一引用给学生。

### 2.4 确定性义务引擎（算法核心步骤）
引擎回答："鉴于代理观察到的一切及其当前提议动作，策略还要求哪些进一步动作？"
- **Step 1：估计动作后环境状态**。设 σ_g 为工具 g 的最新观测，w_1...w_m 为观测后已执行的动作，W_a 为草稿提议动作。引擎按顺序应用所有动作得到投影状态 σ̂ = π(σ_g; w_1..m · W_a)。可预见效果被模拟（受影响状态变量设为参数值，ALL 样式参数影响所有匹配变量）；不可预见或失败的动作标记为未知。**因此草稿自身会创造的违规立即产生修复动作**。
- **Step 2：计算缺失动作**。规则若触发工具已在历史或草稿中使用则是激活的。对每条激活规则、每个投影值违反条件的实体 x，引擎填入动作模板 ω(x)，再去除已执行（E_h）和草稿已包含（A_a）的动作。剩余 Ω 即为**欠账动作**：

  Ω(a, h) = ⋃ [ω(x) : φ ~ x, σ̂(x) ◁ v] \ (E_h ∪ A_a)

- **Step 3：粒度匹配**。若每个实体都违规且工具接受 ALL 风格参数，逐实体动作合并为一个集体动作（与基准评分的中间状态粒度一致）。镜像检查标记多余动作（对豁免实体的动作、只有部分实体符合却用集体动作等）。每条发现都引用可立即执行的动作及观察证据。

### 2.5 Tiered Verification 与 25 个确定性门控
- 围绕义务引擎运行 **25 个确定性门控**，每个门控从回合自身产物（转录、工具模式、先前观测）可判定。表 1 列出了最关键的 7 个（均可发硬发现）：
  | 门控 | 检查内容 |
  |------|----------|
  | 标识符来源 | 所有不透明标识符必须在先前观测返回中出现，禁止发明新标识符 |
  | 模式/枚举有效性 | 参数必须符合工具声明的类型和枚举值 |
  | 先收集后行动 | 规则条件依赖的观测若从未执行，先要求只读调用 |
  | 确认协议 | 需同意策略标注的动作，历史中必须有用户"是/y"的意图确认 |
  | 完成声明 | 回复声称已执行的动作必须实际执行或在草稿中 |
  | 拒绝读取 | 回复说"无法执行"时必须先做对应只读检查 |
  | 未来条件 | 涉及未来时刻的问题须以未来时刻的数据回答，而非当前过滤条件 |
- **算法 2（验证一步）**：
  1. 每个门控 γ ∈ Γ 对同一元组 (a, h, R) 运行，输出硬发现和候选分两个集合累积；门控内部出错则贡献空集——劣质检查不能阻塞良好草稿。
  2. 若有建议候选，LLM 批判器批量对照转录和工具模式确认/丢弃，不得新增或推翻硬发现。
  3. **振荡阀**：丢弃重复要求学生已修订走的动作集的发现，并放松收集门控，防止两个门控互相牵制把草稿来回踢到 R 轮耗尽。
- **分级设计的意义**：硬发现确定正确、必然触发修订，关键检查不依赖采样判断；建议候选本身不确定，且只能被批判器过滤，坏样本最多损失一条建议，绝不会造成假修正或压制硬发现——教师保证优雅降级而非反转。

## 6. 主要结论与发现

- **总成绩超越基线**：Pass 3 提升 3.3 个百分点（53.3 vs 50.0），Pass@3 大幅提升 13.3 个百分点（80.0 vs 66.7），Pass 1 提升 6.7 个百分点（66.7 vs 60.0）。
- **类别差异显著**：
  - **Hallucination 类最好**（70.0/100.0/90.0 vs 基线 50.0/60.0/60.0）：因为标识符是否出现过、参数是否匹配模式都是代码可查的简单事实，无需判断力，结果确定可复现；
  - **Base 类持平**（50.0/60.0/60.0）；
  - **Disambiguation 类最差**（40.0/80.0/50.0）：代码能确认"是否提问并获同意"，但无法判断"是否应该提问"，这取决于语义歧义性判断，留给 LLM 批判器而批判器并非总是正确。
- **框架价值确认**：框架"让好尝试变得更好"——它在动作到达驾驶员之前移除错误；但它"不能让三次尝试更相似"，因为学生每次写出不同草稿。
- **主要瓶颈**：Pass@3（80.0）与 Pass 3（53.3）之间的差距（8 个任务部分尝试成功）来自学生不稳定性，且当没有编译规则覆盖任务时检查是沉默的。因此提升 Pass 3 的关键是**将更多策略转化为可执行规则**。

- **缺乏消融实验**：论文未量化验证框架各组件（义务引擎、25 个门控、LLM 批判器、多模态投票、安全网）各自的贡献，也无法回答“哪个组件最关键”或“去掉某组件后性能掉多少”的问题，这使框架设计更像工程化拼装而非科学归因。
- **策略编译覆盖决定系统上限**：没有可执行规则覆盖的任务上，验证是沉默的，只能靠学生自生能力兜底。这意味着框架的实际收益高度依赖人工/半自动地把自然语言策略转化为规则的质量与覆盖面，而这一部分是论文中描述得最繁重、也最不自动化的环节。
- **成本开销显著**：每回合 19.2 秒、362k tokens，约为基线 3.2 秒、82k tokens 的 4–6 倍。尽管论文指出排行榜上 token 消耗与成绩不相关（r = 0.435），但真实部署中延迟和成本仍是硬约束，论文未给出可接受的部署成本论证。
- **Disambiguation 类本质未解决**：代码能验证“是否已询问、是否已获确认”，却无法验证“该不该问、该问什么”，这部分仍交给 LLM 批判器判断，结果最差（Pass 1 仅 50.0）。框架转移了确定性错误，但并未消除语义歧义判断这一根本难点。
- **单模型评估**：仅用 Claude Opus 4.8 作为学生，未验证其他 LLM 下该框架是否同样有效；考虑到框架绕过模型判断依赖确定性门控，理论上模型无关性应被实验证明确认。
- **论文未报告硬件资源细节**，且所有结论建立在单一 benchmark 的隐藏测试集上，外部效度有待检验。

## 9. 改进建议与未来方向

- **补消融与多模型实验**：逐一关闭义务引擎、批判器、投票、安全网，给出各组件的边际贡献曲线；同时用不同规模的多种 LLM 作为学生重复实验，验证框架的模型无关性。
- **扩大策略编译覆盖**：论文明确指出 Pass 3 提升的关键在于把更多策略转化为可执行规则，因此应把策略编译从人工编写升级为“LLM 起草 + 确定性校验 + 人工审核”的半自动流水线，并建立规则覆盖率与任务成功率之间的量化关系。
- **改进歧义判断机制**：对需要在何时提问、问什么的语义判断，可尝试引入形式化偏好模型、基于信息增益的主动询问策略，或让批判器基于任务模板而非自然语言来完成判断，减少对模型直觉的依赖。
- **优化推理成本**：多模态投票与多轮验证-修订是 token 消耗的主要来源，可尝试自适应决定投票次数（例如此前已成功执行过相似工具序列时减少采样）、缓存批判器判定结果、以及用轻量模型替代高成本模型做候选筛选。
- **更强的安全保证形式化**：当前规则仍以代码方式存在，缺乏对规则之间冲突、规则覆盖完备性的形式化分析；未来可以引入三类证明——工具调用与策略的一致性证明、环境状态投影的可靠性证明、以及终止性与无死锁证明，从而把“验证”提升为“保证”。

## 10. 总体评价

AgentGuardUtil 的贡献不在于让模型变得更强，而在于重新划定了“模型负责什么、代码负责什么”的边界：LLM 只做它擅长的语义理解与提议生成，一切可判定的正确性检查全部移交给确定性框架，并在动作到达环境前强制实施“验证—修订”闭环。这种假设-保证式的架构设计是合理且可迁移的，与 CAR-bench 对可验证、可复现系统能力的考察目标高度契合。

但就文本呈现而言，该工作仍停留在“工程系统报告”而非“充分科学验证”的层次：实验规模小、无消融、单模型、成本未权衡，均限制了结论的强度；其真正竞争力——策略编译覆盖率与 25 个门控的完备性——也没有被系统性地证明或与其他方法对齐比较。因此，本文的结论应被理解为：在有限测试集上，确定性验证框架能稳定提升 LLM 车载智能体对可编码策略的依从性，降低而非消除因模型不稳定带来的任务失败风险。未来若能在更多模型、更多任务和更严格消融下复现该结果，这套“学生提出、教师裁决”的架构有望成为安全攸关 LLM 智能体的通用设计范式。

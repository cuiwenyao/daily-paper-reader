# ABDA -NL : A Natural-Language Scenario Explorer for Argument-Based Reasoning 

## Extended Version of the COMMA 2026 Demonstration Abstract 

Shawn BOWERS a, Martin CAMINADA b, Haoyang LIU c, Bertram LUDÄSCHER ca Gonzaga University, Washington, USA 

b Cardiff University, Wales, UK 

c University of Illinois Urbana-Champaign, USA 

Abstract. ABDA -NL adds a natural-language interface to ABDA , a system for argument-based discussion using ASPIC - knowledge bases under grounded seman-tics. Users see which conclusions are accepted, rejected, or undecided, open an in-teractive rendering of the grounded discussion game to learn why, explore what-if alternatives by suspending assumptions and rules or changing preferences, ask questions that are answered from a scenario’s reference documents, and author new facts, assumptions, and rules in plain English. A large language model provides the bridge between language and formalism: it answers questions from the documents and the current state of the scenario, and it translates plain-English edits into can-didate formal statements. The deterministic ABDA engine remains the sole source of arguments, attacks, and acceptance labels, and every proposal of the model is validated and confirmed by the user before it takes effect. 

1. Introduction 

Informal argumentation typically involves discussion in which parties exchange claims, raise objections, and defend their positions [1]. In contrast, formal argumentation of-ten focuses on computing which claims are accepted from a graph of arguments and their attacks, treating acceptance as a static property rather than the outcome of dialog [2]. The ABDA (Argument-Based Discussion using ASPIC -) system [3] allows users to play a grounded discussion game over ASPIC - knowledge bases [4], a formalism with strict and defeasible rules, strong negation, defeasible assumptions, and rule preferences. However, ABDA still operates at the formal level, where propositions appear as ASPIC -symbols, discussion games are played via formal move primitives, and explanations of moves and outcomes are not given. We present ABDA -NL (github.com/idaks/ABDA-NL ), a web-based tool that extends ABDA with a natural-language user interface: users in-spect, explore, and extend scenarios without needing to engage in ASPIC - notation, while 

ABDA ’s reasoning over the argumentation framework stays authoritative, so that conclu-sions are formally grounded, inspectable, and contestable. Fig. 1 illustrates the tool on a well-known legal case ( Popov v. Hayashi ) formally modeled using strict and defeasible rules in [5]. arXiv:2610.00947v1 [cs.AI] 1 Oct 2026 Figure 1. ABDA -NL on Popov v. Hayashi [5]: the ASPIC - scenario explorer with corpus-grounded chat. 

This paper extends the two-page abstract that accompanies our demonstration at COMMA 2026 [6] with the formal background (Section 2), a description of the system and a walkthrough of a session (Sections 3 and 4), an account of how the language model and the argumentation engine share the work (Section 5), and the features added since the camera-ready version (Section 6). 

2. Background: ASPIC - and the Grounded Discussion Game 

An ASPIC - knowledge base [4] consists of strict rules p 1, . . . , pn → c, which admit no exceptions, and defeasible rules p 1, . . . , pn ⇒ c, which hold normally but may have ex-ceptions. Facts are strict rules without premises, and assumptions are defeasible rules without premises. Literals are atoms or their strong negations (written −p), and each defeasible rule has a name r that can itself be negated, so that a rule concluding −r ex-presses an exception to r. Arguments are built by chaining rules. An argument A attacks an argument B if the conclusion of A is the negation of the conclusion of B or of one of B’s sub-arguments ( rebut ), or the negation of the name of a defeasible rule used in 

B (undercut ). Because facts and assumptions are rules without premises, an attack on a premise, called undermining in ASPIC +, is simply a rebut of that sub-argument here. 

> ASPIC

- differs from ASPIC + [7] in allowing unrestricted rebut, that is, rebuttal of any sub-argument regardless of whether its top rule is strict or defeasible, a choice that an empirical study found to be closer to how people evaluate arguments [8]. Preferences are expressed by assigning defeasible rules and assumptions to strength levels, called blocks 

in ABDA . Arguments are compared by the weakest-link principle with democratic order-ing: a rebut succeeds only if the attacker is not weaker than the sub-argument it attacks, whereas undercuts always succeed. The arguments and successful attacks form a Dung-style argumentation framework [9], which ASPIC - evaluates under grounded semantics. Every argument receives one of the labels in , out , or undec [2], and a literal is accepted 

if it is the conclusion of an in argument, undecided if it is the conclusion of an undec 

argument but of no in argument, and rejected otherwise. Grounded semantics can be explained through the Grounded Discussion Game [10], a dialog between a proponent and an opponent that is sound and complete for grounded semantics: the proponent has a winning strategy for an argument A if and only if A is in the grounded extension. The game has four moves. HTB (A), “ A has to be the case,” is the proponent’s move; it opens the game with the main argument and is later used to defend against challenges. CB (B), “ B can be the case,” is the opponent’s move; B

must attack the argument of the most recent HTB move that has not yet been conceded. 

> CONCEDE

(A) is played by the opponent once every attacker of A has been retracted, and 

> RETRACT

(B) once some attacker of B has been conceded. The discussion ends when no move is possible, in particular once an argument has been used twice, by one player or by both; the proponent wins if the main argument has been conceded, and the opponent wins otherwise. ABDA [3] lets a user play this game against the system through these move primitives over formal ASPIC - arguments; ABDA -NL renders the same dialectical structure in natural language (Section 4). 

3. ABDA -NL : Scenarios, Architecture, and Interface 

Scenarios A scenario in ABDA -NL consists of an ASPIC - knowledge base, a glossary, and a corpus of reference documents. The knowledge base is stored as a YAML file that declares facts, assumptions, intermediate propositions, key conclusions, and rules, each with an identifier; assumptions and defeasible rules also carry a strength block and an 

active flag that allows them to be suspended. The glossary maps every identifier to a plain-language description and, where needed, to the wording of its negation. The four rules below, taken from Popov v. Hayashi and shown with their rendering, illustrate the format. The first two rebut each other, since their conclusions are opposite literals. The fourth concludes the negation of the name of the third, so an argument built with it un-dercuts every argument that uses rule wt1 . Its first premise is an assumption: the scenario treats the validity of each commonsense or legal principle as a defeasible premise that can itself be contested.               

> popov_qual_right => -hayashi_no_return [rp]
> IF Popov has a qualified right to possession of the baseball THEN NORMALLY Hayashi has to return the baseball
> hayashi_legit_claim => hayashi_no_return [rh]
> IF Hayashi has a legitimate claim to the baseball THEN NORMALLY Hayashi does not have to return the baseball
> popov_testimony_control => popov_had_full_control [wt1]
> IF Popov testified that he had full control of the baseball when he was attacked THEN NORMALLY Popov had full control when he was attacked
> cs3_valid, testimony_inconsistent => -wt1 [cs3]
> IF inconsistent testimony is unreliable (cs3) AND Popov’s testimony is inconsistent, ambiguous, and unconvincing THEN NORMALLY Popov’s control-testimony doesn’t stand on its own (wt1)

Each identifier is rendered by its description, a negated literal by the wording of its nega-tion, and the negated rule name -wt1 by the wording recorded for the exception to wt1 .The knowledge base of Popov v. Hayashi is based on Prakken’s reconstruction [5], and its corpus holds the court’s ruling, a law review article, a Wikipedia article, and a short blog commentary. The corpus serves only as context for the language model; it never enters the reasoning. ABDA -NL ships with six scenarios: Popov v. Hayashi (19 facts, 20 assumptions, 38 rules, and 8 key conclusions, yielding 77 arguments and 24 attacks) and five smaller decisions from everyday life, medicine, environmental management, and sports. 

Architecture ABDA -NL has three layers. The deterministic core embeds the ABDA en-gine as an in-process library. After every change it rebuilds all arguments and attacks from the current knowledge base, computes the grounded labeling, and derives the label of every proposition. This takes milliseconds for the built-in scenarios, and limits on the number of arguments and attacks the engine will construct keep a pathological knowl-edge base from stalling the server. The rendering layer turns formal objects into natural language purely through templates over the glossary: rules become IF /THEN sentences that read “necessarily” for strict and “normally” for defeasible rules, and the panels, the explanation trace, the conclusion graph, and the raw ASPIC - listing are all generated from the same computed framework. The third layer consists of optional language-model ser-vices for question answering and natural-language authoring (Section 5); without them, 

> ABDA

-NL runs in a basic mode in which every argumentation feature remains available. 

Interface The main view (Fig. 1) has four panels: a conclusions dashboard (upper left) with the labels accepted , rejected , and undecided , plus absent for a key conclusion that the current knowledge base cannot derive either way; the facts and assumptions (upper center); the rules (bottom); and a chat panel (right). Every item shows its identifier next to its description, so that the natural-language and the formal views stay connected, and filters restrict each list. 

4. Using the Demo 

Inspect conclusions After loading a scenario, the user reads the key conclusions and their labels. In Popov v. Hayashi , for example, “Popov has a legitimate claim to the baseball” and “Hayashi has a legitimate claim to the baseball” are both accepted, whereas “Popov has possession of the baseball” is rejected. 

Explain Clicking Explain on a conclusion opens the explanation view (Fig. 2, left), which is organized as the grounded discussion game would unfold. The root card, la-beled Proponent: Has to be the case , is the proponent’s HTB move for an argument with the chosen conclusion; it shows the rule that derives the conclusion and expands to its premises and sub-arguments down to the facts. Each card labeled Opponent: Can be the case that is an opponent’s CB move: a counter-argument that rebuts the conclusion of a sub-argument or undercuts one of its defeasible rules, with the kind of attack stated. Ex-panding a challenge reveals the proponent’s replies. Rather than taking turns, the user ex-plores the whole tree, and the end of each branch is worded as the game outcome would be: a challenge is retracted when a defense exists, stands when no defense is available, and a claim is conceded when every challenge against it has been answered. Derivations of the opposite conclusion that produce no attack, as happens when a preference blocks a rebut, are listed where the branch ends, and mutual attacks among undecided arguments are reported as a cycle. Only counter-arguments that matter under grounded semantics are shown, which keeps the tree small. Figure 2. Interactive explanation via the discussion game (left) and natural-language rule authoring (right). 

Explore what-if alternatives Assumptions and defeasible rules have a toggle that sus-pends them. Before a toggle takes effect, ABDA -NL recomputes the scenario and shows which conclusions would change label; activating the equity assumption in Popov v. Hayashi , for example, turns “the ball’s proceeds should be divided equally between Popov and Hayashi” from absent to undecided. The user can then apply or cancel. The 

Conflicts tab of the rules panel lists pairs of defeasible rules whose conclusions contradict each other (an assumption can take the place of a rule) and lets the user prefer one side or restore equal priority, which ABDA -NL translates into strength blocks. Conclusions whose label changed are highlighted, an indicator counts the changes from the baseline, and Reset restores it, with an undo. 

Ask questions The chat panel answers questions about the case from the corpus and from the current state of the scenario, citing the documents it used (Fig. 1, right). A sparkle icon next to any conclusion, fact, assumption, or rule adds that item to the ques-tion being composed. 

Author statements Through + Add in the facts panel, + Add rule , or Modify with AI on a rule, the user describes the intended statement in plain English. ABDA -NL proposes a formalization, shows it both as a sentence and in ASPIC - syntax together with advisory review notes (Fig. 2, right), and lets the user refine the request, cancel, or apply. On apply,  

> ABDA

recomputes all labels. 

Inspect the framework Conclusion graph draws the argumentation framework aggre-gated by conclusion, with colors for labels and distinct edge styles for mutual rebuts, one-way rebuts, and undercuts; any node opens the derivations of its literal. ASPIC - text 

lists the current knowledge base, including glossary comments and suspension markers, in a form that can be re-imported. 

5. The Role of the Language Model 

> ABDA

-NL pairs a symbolic engine with a large language model and gives each the part of the work it is good at. ABDA decides what follows from a knowledge base: it constructs the arguments and attacks and computes the grounded labels, deterministically and for every change. The language model handles language: it answers questions from the sce-nario’s documents and current state, and it turns a plain-English request into a candi-date formal statement. The text of the interface itself, from rule sentences to the expla-nation trace, is generated from the glossary by templates, so a scenario can be explored, explained, and edited by hand without any model, and whatever a model contributes is visible as such. The two calls, and the checks around each, are described below. 

Grounded question answering For each question, ABDA -NL assembles context of two kinds. From the corpus it selects passages by a deterministic lexical ranking that keeps at least one excerpt from every document and records where each excerpt occurs. From the engine it builds a description of the current state: the label of every key conclusion together with the rules that support, oppose, or undercut it, the state of every assumption, the arguments with their labels and defeats, and any changes made to the baseline. An item added to the question through its sparkle icon is passed by identity, so that its formal definition and its role in the framework are in view. The prompt names the engine as the authority on what is warranted and asks the model to restate its labels, to quote sources verbatim and cite the file each quote comes from, to decline questions outside the scenario, and to ignore instructions that appear inside documents. Before an answer is shown, the server checks every citation against the corpus and every quotation against the exact passages it supplied; a draft that fails is returned to the model once with the problem, and if the second draft fails too, the user sees a short notice. Verified excerpts are displayed with the answer and can be opened at their location in the source (Fig. 1, right). Within these bounds the model does what a symbolic engine cannot: it relates the formal outcome to the facts of the case in fluent prose, grounds its account in the documents, and answers follow-up questions in context. 

Natural-language authoring When a user describes a new fact, assumption, or rule in plain English, the model acts as a translator into ASPIC -. It receives the request together with the current state of the scenario and must return a structured proposal through a schema-constrained tool call: the operation, premises and conclusion as identifiers, the rule type and strength block, and a glossary entry for every new identifier. The prompt directs it to reuse existing identifiers wherever the request refers to an existing statement. The proposal is then checked deterministically. Malformed payloads, missing or collid-ing identifiers, references to unknown rules, and structurally impossible combinations are rejected; the model is then told what was wrong and asked for a new proposal, and if three attempts fail, the request is abandoned and the problems are reported to the user. A second, advisory model call reviews the surviving proposal against the scenario and flags concerns such as a mismatch between the request and the formalization, a descrip-tion that contradicts the formal content, or redundancy with an existing rule; these notes are shown but do not block. Finally, the user sees the proposal both as a sentence and in 

> ASPIC

- syntax (Fig. 2, right) and decides whether to refine, cancel, or apply it. Nothing is applied automatically, and an applied rule is treated exactly like a hand-written one. The formalization of a free-text request is not unique, and two runs may propose different candidates, for instance one that reuses an existing proposition and one that introduces a new one. The design does not depend on the model being deterministic: whatever is applied is well-formed, refers only to declared symbols, has been seen by the user in its exact formal form, and has its consequences computed by the engine. Scenario files and imported ASPIC - text are parsed and validated by a deterministic loader. Figure 3. Creating a scenario in the Guided view, with its labels computed by ABDA in the preview (left), and the sources reader showing a quotation verified against the saved document (right). 

Models and their qualification The hosted service offers several models from different providers, and users may also bring a key of their own. A model is admitted to this set only after passing an evaluation suite of question-answering and authoring cases over all built-in scenarios, run repeatedly: every case must pass in every repetition, every quotation must be found verbatim in the corpus, every acceptance status reported must agree with the engine, and every proposal must match the expected operation. If a model call fails, the chat says so and everything else continues to work. 

6. New Features Since the Camera-Ready Version 

Hosted service ABDA -NL now runs as a public service at demo.abda-nl.org , so that anyone can explore the built-in scenarios without installing anything or signing in. Model-assisted features require a verified email sign-in; the user then picks one of sev-eral qualified models and pays for it either from funded trial credit, offered to a limited number of users, or with an API key of their own, which is held in the browser tab only. The interface is keyboard-operable and passes automated accessibility checks at WCAG levels A and AA. 

Scenario authoring and exchange Users are no longer limited to the scenarios we ship. A unified editor (Fig. 3, left) lets them build their own: in the Guided view, statements are written in plain English, typed as facts, assumptions, or claims, and connected by 

> IF

/THEN rules marked as strict or defeasible, while the Rule text view shows and edits the same knowledge base in ASPIC - syntax. Statement descriptions double as the glossary, symbols can be renamed with every reference rewritten consistently, and reference doc-uments (text, Markdown, or text-based PDF) can be attached to give the chat something to cite, without becoming logical facts. Check & save validates the draft and saves it as a private scenario, Preview shows the computed ABDA results first, and neither needs a model call. Scenarios can be imported from YAML or JSON files or from ASPIC - rule text with a glossary, and exported as one self-contained JSON file that carries the full reference text and opens on any installation. Private scenarios, sharing, and community scenarios Signed-in users save their work as private scenarios, which then serve as the baseline for further exploration and ques-tions; saves are version-checked, so two browser tabs cannot silently overwrite each other. A scenario can be shared through a revocable read-only link: recipients can inspect and explain it but not modify it, and may save a private copy to continue on their own. A scenario that others might learn from can be suggested to the community; after the author’s explicit consent and a curator’s review, it is listed next to the built-in scenarios for every visitor. 

Chat and exploration The chat has grown into a workspace for exploring a scenario. Items added with the sparkle icon become removable references inside an editable ques-tion, so a user can point at a rule or a conclusion and ask about it in their own words. Conversations are saved and can be exported; any earlier question can be edited into a new branch or retried, and each question keeps the scenario state it was asked about. Evidence cards open the cited passage in a reader for the scenario’s documents and glos-sary (Fig. 3, right). On the formal side, a Derivation view beside Explain shows any sin-gle argument with its premises, sub-arguments, rules, label, and attacks, linking each natural-language item to its exact ASPIC - counterpart. 

Agent access ABDA -NL also exposes a Model Context Protocol (MCP) 1 server, so that AI coding agents such as Codex and Claude Code can operate the tool under a personal, revocable token with explicit scopes. Read tools list and open built-in, community, and private scenarios together with their grounded outcomes; write tools create private sce-narios and apply version-checked edits, after which the engine recomputes; and two me-tered tools ask grounded questions and request proposals. A proposal returned to an agent is never applied by the server: the agent must review and apply it explicitly, subject to the same checks as in the browser. Reading and editing consume no model credit, so an agent’s own model can drive an explore, edit, and verify loop against ABDA .

The source code of ABDA -NL is available at github .com/idaks/ABDA-NL and the hosted service at demo .abda-nl .org ; the system was demonstrated at COMMA 2026.
